# Requirements: Milestone v4.0 (Consistência Lógica e Regras de Negócio)

Este documento descreve os requisitos funcionais e não-funcionais que compõem a Milestone v4.0, focada na correção de falhas lógicas, usabilidade diária e segurança de regras de negócio.

---

## 1. Módulo de Empréstimos e Datas

### [REQ-401] Validação de Datas de Empréstimo
- **Descrição:** O sistema deve impedir que datas inválidas ou ilógicas sejam definidas.
- **Critérios de Aceitação:**
  - A data de solicitação (`loanDate`) e de devolução (`dueDate`) não podem ser anteriores à data atual.
  - A data de devolução (`dueDate`) deve ser posterior à data do empréstimo (`loanDate`).
  - O sistema deve validar e definir um limite de tempo máximo razoável para empréstimos (ex: no máximo 30 dias).
  - Erros de validação devem ser informados de forma clara tanto no backend quanto no frontend.

### [REQ-402] Segurança na Identificação do Solicitante
- **Descrição:** O formulário de empréstimo do frontend não deve permitir que o solicitante se passe por outro usuário informando nome/e-mail de terceiros.
- **Critérios de Aceitação:**
  - Se o usuário logado for do tipo comum (ex: Aluno/Estagiário), os campos "Nome do Solicitante" e "E-mail" devem ser automaticamente preenchidos com os dados da sua sessão (`AuthContext`) e bloqueados para edição (`disabled`/`readOnly`).
  - Se o usuário for um administrador/laboratorista criando um empréstimo diretamente no painel admin, ele poderá ter a opção de escolher outro usuário para registrar o empréstimo (opcional).
  - O backend deve sempre validar que o ID do solicitante enviado corresponde ao usuário autenticado (ou ao usuário selecionado se for admin).

---

## 2. Cadastro e Segurança de Contas

### [REQ-403] Criação Administrativa de Usuários
- **Descrição:** O administrador deve conseguir criar novos usuários diretamente na aba administrativa "Usuários".
- **Critérios de Aceitação:**
  - Criação de uma rota `POST /users` no backend exclusiva para administradores.
  - O administrador deve conseguir selecionar a Tag (Perfil) e definir o status `isActive` (Ativo/Inativo) diretamente no formulário de criação.
  - O frontend deve usar esse novo endpoint ao invés do endpoint público de registro (`/auth/register`).

### [REQ-404] Unicidade de Matrícula e E-mail
- **Descrição:** O sistema deve garantir que não existam dois usuários cadastrados com o mesmo e-mail ou a mesma matrícula.
- **Critérios de Aceitação:**
  - Tanto no registro público quanto na criação/edição pelo administrador, o backend deve validar se o `email` ou a `matricula` informados já existem na base de dados.
  - Retornar um erro HTTP 400 amigável especificando qual campo está duplicado (ex: "Esta matrícula já está cadastrada").

### [REQ-405] Senha Provisória e Troca Obrigatória
- **Descrição:** Usuários criados manualmente pelo administrador devem ter uma senha provisória e ser forçados a alterá-la no primeiro acesso.
- **Critérios de Aceitação:**
  - O banco de dados deve rastrear se o usuário precisa alterar a senha (ex: campo `mustChangePassword` na tabela `users`).
  - Ao criar um usuário na aba admin, o campo `mustChangePassword` deve ser definido como `true`.
  - Ao realizar login, se o campo for `true`, o frontend deve exibir obrigatoriamente uma tela ou modal para alteração de senha antes de dar acesso a qualquer outra funcionalidade do sistema.
  - Após atualizar a senha, o campo `mustChangePassword` é definido como `false`.

## 3. Estoque e Estado de Itens

### [REQ-406] Desativação Silenciosa de Itens (Soft Hide)
- **Descrição:** O administrador deve poder ocultar itens do catálogo geral sem excluí-los fisicamente do banco de dados, para preservar o histórico de empréstimos antigos associados àquele item.
- **Critérios de Aceitação:**
  - O painel de estoque do administrador deve conter um toggle "Ativo" para ligar/desligar cada item.
  - Itens inativos (`isActive: false`) não devem aparecer na busca pública ou catálogo (`/items`).
  - O botão "Excluir" continuará existindo e deletará fisicamente o item apenas se não houver empréstimos vinculados a ele (impedindo erros de integridade).

---

## 4. UI e Auditoria Preventiva

### [REQ-407] Ajustes e Polimentos Visuais
- **Descrição:** Corrigir pequenos erros de alinhamento e centralização nas telas.
- **Critérios de Aceitação:**
  - Na página de detalhes do item (`/inventory/[id]`), alinhar verticalmente o link de navegação "← Catálogo" com o botão "Ir para o carrinho".
  - Corrigir a centralização e o alinhamento das setas/ícones de chevron nos filtros de busca e categorias no catálogo.

### [REQ-408] Auditoria Geral de Falhas Lógicas
- **Descrição:** Evitar falhas críticas de negócio no fluxo do sistema.
- **Critérios de Aceitação:**
  - Garantir que itens com estoque zerado ou quantidade indisponível não possam ser adicionados ao carrinho ou solicitados.
  - Garantir que a quantidade de itens em um empréstimo não possa ser negativa ou fracionada.
  - Bloquear a auto-aprovação de empréstimos (um usuário que possua permissão de aprovação não deve conseguir aprovar seus próprios pedidos pendentes).
